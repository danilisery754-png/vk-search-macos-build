# VK Outreach Manager — проектное решение

Дата: 2026-08-24  
Целевая платформа: Windows 10 x64 (1809/LTSC 2019, build 17763+) и Windows 11 x64.  
Пользователь: один локальный оператор, несколько независимых VK-аккаунтов.

## Подтверждённая основа VK

- Договоры методов сверены с официальной схемой VK API 5.199.
- `messages.send` допускает пользовательский токен, `peer_id` и `random_id`. `random_id` используется как первый уровень дедупликации.
- `messages.getConversations` и `messages.getHistory` допускают пользовательский токен и являются основой единого окна сообщений.
- `wall.post` документирован для пользовательского токена и публикации записей, включая предложенные записи. Реальная возможность предложить запись конкретному сообществу всё равно определяется живым ответом API.
- Реальная доступность методов и scopes для вновь полученного токена не считается подтверждённой до LIVE-проверки на пользовательском аккаунте.

## Авторизация аккаунтов

Используется перенесённая из рабочего проекта браузерная схема:

1. Для аккаунта создаётся отдельный постоянный browser-profile.
2. Открывается видимое окно Edge/Chromium.
3. Оператор проходит VK-вход, 2FA или captcha самостоятельно.
4. Приложение автоматически проходит только известные безопасные экраны подтверждения.
5. Токен перехватывается в памяти, сразу маскируется и проверяется через `users.get`.
6. Подтверждённые `vk_user_id`, имя и аватар привязываются к аккаунту.
7. Токен шифруется Windows DPAPI для текущего пользователя; открытым текстом в БД и логах не хранится.
8. При истечении выполняется тихая повторная авторизация через сохранённый профиль. Подмена личности отклоняется.

Основной браузер — системный Edge. Запасной — поставляемый Chromium. UI и очередь не зависят от открытого браузера.

## Отправка и классификация

Для одной зарезервированной группы выполняются два независимых направления:

- ЛС: `messages.send(peer_id=-community_id, message=..., random_id=...)`.
- Предложенная запись: `wall.post(owner_id=-community_id, message=...)` при доступности операции для аккаунта.

Каждая попытка получает стабильный idempotency key. Ответ API сначала сохраняется как сырое диагностическое событие с маскированием секретов, затем нормализуется в один из классов:

- подтверждённый успех;
- подтверждённая невозможность;
- временная ошибка;
- требуется повторный вход;
- неизвестная ошибка.

Неизвестная или временная ошибка не превращается автоматически в окончательный отказ. После ограниченных повторов задача остаётся прозрачно диагностируемой, без бесконечного цикла.

## Технологический стек

- Python 3.13.15, встроенный в Windows-сборку.
- FastAPI — внутренний локальный API и WebSocket-события.
- SQLAlchemy 2 + Alembic + SQLite WAL, foreign keys и `busy_timeout`.
- React + TypeScript + Vite, TanStack Query/Table/Virtual.
- pywebview + Edge WebView2 — отдельное нативное окно Windows и системный трей.
- Playwright/Edge adapter — браузерная авторизация и fallback.
- httpx — VK API.
- PyInstaller onedir — portable runtime; Inno Setup — установщик.

`onedir` выбран вместо одного гигантского exe: быстрее запуск, надёжнее обновление ресурсов и браузерного драйвера.

## Слои проекта

- `desktop` — окно, трей, single-instance, запуск/остановка ядра.
- `api` — локальные endpoints и WebSocket; VK напрямую не вызывает.
- `services` — аккаунты, группы, результаты, inbox, экспорт, настройки.
- `vk` — клиент API, browser auth, классификатор ошибок.
- `workers` — supervisor, независимый worker на активный аккаунт.
- `db` — модели, транзакции, миграции, recovery.
- `frontend` — русскоязычное рабочее пространство.

## Схема данных

Ключевые таблицы:

- `accounts`: личность, заметка, состояние и счётчики.
- `account_secrets`: DPAPI-зашифрованный токен и browser-profile.
- `settings`: типизированные постоянные настройки.
- `communities`: канонический VK id, screen name, ссылка и название.
- `runs`: техническая история запусков без навязывания «кампаний» в UX.
- `work_items`: активное/завершённое состояние, владелец reservation, lease и номер попытки.
- `send_attempts`: направление, idempotency key, VK request id/result/error class.
- `results`: отдельные результаты ЛС/предложки и итог.
- `dialogs`, `messages`: локальный кэш inbox с жёсткой привязкой к аккаунту.
- `event_logs`: пользовательские и технические события.

Уникальности не запрещают повторно добавить группу в будущем: уникален `community_id` внутри одного `run`, а не навсегда.

## Распределение и очередь

При старте создаётся технический `run`. Активные группы перемешиваются криптографически стойким генератором и распределяются round-robin между активными аккаунтами, пока каждый не достигнет собственного лимита.

Claim выполняется в короткой транзакции `BEGIN IMMEDIATE`: item переходит из `assigned` в `processing`, получает `lease_owner` и `lease_expires_at`. Поэтому два worker-а не могут взять одну строку.

У каждого аккаунта отдельный последовательный worker и собственная задержка. Разные аккаунты работают параллельно. Ошибка одного не останавливает supervisor.

## Crash recovery и защита от дублей

- Перед внешним действием создаётся `send_attempt` с уникальным idempotency key.
- Для `messages.send` из ключа детерминированно получается ненулевой `random_id`.
- После ответа VK попытка фиксируется отдельной короткой транзакцией.
- Просроченные leases возвращаются не прямо в отправку, а в `reconcile_required`.
- Если ответ мог успеть пройти, выполняется безопасная сверка истории/результата; слепая повторная отправка запрещена.
- Двойное нажатие «Запустить» блокируется single-flight состоянием.
- SQLite работает в WAL; записи сериализуются короткими транзакциями, сеть внутри транзакций не вызывается.

## Единый inbox

Фоновая синхронизация по каждому аккаунту получает диалоги и непрочитанные независимо от рассылки. UI показывает группы аккаунтов, фильтры «Все / Непрочитанные / Прочитанные», поиск и master-detail диалог. Перед отправкой ответа сервер повторно проверяет `account_id`, а UI явно показывает «Вы отвечаете от…».

Если API конкретного токена не позволяет читать/отвечать, кнопка «Открыть сообщения» запускает сохранённый профиль нужного аккаунта. Это fallback, а не основной режим.

## UI

Экраны: Главная, Список групп, Сообщения, Успешно написали, Не удалось написать, Аккаунты, Логи, Настройки. Результаты физически разведены по разным маршрутам и запросам. Таблицы имеют поиск, сортировку, фильтры, выбор, виртуализацию, TSV-копирование и TXT/CSV/XLSX-экспорт.

## Проверки готовности

- Unit: нормализация, dedupe, балансировка, per-account limit, outcome, retry, экспорт.
- DB integration: атомарный claim, concurrent claim, recovery, повторный старт, изоляция аккаунтов.
- VK contract: mock server для всех классов ошибок; отдельный LIVE checklist без подмены его моками.
- UI: маршруты, таблицы, выбранные строки, копирование, inbox account binding.
- Windows: чистые VM Windows 10 build 17763 и Windows 11; установка, запуск, auth, restart/recovery, portable, uninstall.

## Основные риски

1. VK может изменить OAuth или ограничения пользовательских токенов. Мера: browser adapter, валидатор identity, fallback и LIVE registry.
2. Успешный ответ VK может потеряться из-за падения. Мера: deterministic idempotency, attempt journal и reconcile.
3. SQLite contention. Мера: WAL, busy timeout, короткие транзакции и один writer boundary.
4. Win10/browser compatibility. Мера: WebView2, Edge-first auth, bundled Chromium fallback и отдельная clean-VM проверка.
